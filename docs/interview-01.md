# EXERCISE 9-3 — SKOPE 인터뷰 기록 초안

> 아래 고객 발언과 결산은 **가상 답변을 사용한 작성 예시**이다. 실제 인터뷰를 수행한 기록이 아니므로, 인터뷰 후 실제 발언과 도출 결과로 바꾸어 제출한다.

## 1. 인터뷰 개요

- 프로젝트: SKOPE — 서경대학교 AI 캠퍼스 문제 관리 시스템
- 대상: 교내 시설·IT·학사·학생복지 관련 문제를 경험한 학생
- 인터뷰 일시·상대 팀·참여자: 실제 인터뷰 후 기입
- 목적: 교내 문제를 알리고 처리 결과를 확인하는 과정의 불편을 파악하고, 기존 기획에서 빠진 요구를 찾는다.
- 비교 기준: 현재 EX 10-4 SRS의 문제 접수·AI 분류·담당 부서 연결·처리 추적·반복 이슈 탐지 5개 기능. 전체 팀 백로그와의 중복 여부는 인터뷰 후 확인한다.

## 2. 준비 질문 5개

1. 최근 학교생활 중 불편한 문제를 겪었던 경험을 이야기해 주세요. 그 문제를 알리기 위해 어떤 행동을 하셨나요?
2. 문제를 알린 뒤 담당자와 설명을 주고받는 과정은 어땠나요? 가장 어려웠던 점을 이야기해 주세요.
3. 문제가 해결되었는지는 어떻게 확인하셨나요? 안내받은 결과와 실제 상황이 달랐던 경험이 있다면 말씀해 주세요.
4. 학교의 문의·신고 창구를 처음 이용했을 때 어떤 과정에서 막혔나요? 당시 어떻게 해결하셨나요?
5. 문의를 제출한 뒤 접수 여부를 확인하기까지 얼마나 기다렸나요? 기다리는 동안 어떤 행동을 하셨나요?

공통 후속 질문: “왜 그 점이 불편했나요?”, “그때 어떻게 해결했나요?”, “그 결과 어떤 문제가 남았나요?”를 답변에 따라 이어서 묻는다.

## 3. 인터뷰 기록표 — 가상 답변 예시

F는 기능 요구, NF는 비기능 요구를 뜻한다. 실제 기록에서는 고객이 말한 표현을 가능한 그대로 남긴다.

| 기록 ID | 고객 발언 예시 | 추정되는 요구 | F/NF | 후속 질문 메모 |
|---|---|---|---|---|
| I-01 / 질문 1 | “강의실 의자가 고장 났는데 어디로 연락해야 할지 몰라서 학과 사무실에 먼저 물어봤어요.” | 담당 부서를 몰라도 문제를 접수하고 관련 부서에 연결할 수 있어야 한다. 기존 FR-01·FR-03과 관련된다. | F | “연락할 곳을 찾는 과정에서 무엇이 가장 어려웠나요?” |
| I-02 / 질문 2 | “어느 강의실의 어떤 의자인지 다시 설명해 달라고 연락이 왔어요. 처음 보낸 내용과 추가 설명을 따로 보내니까 어디까지 전달됐는지 헷갈렸어요.” | 담당자의 보완 요청과 신고자의 추가 답변을 같은 접수 건에서 주고받을 수 있어야 한다. | F | “추가 설명을 어떤 경로로 전달했고, 무엇을 다시 설명해야 했나요?” |
| I-03 / 질문 3 | “처리됐다고 안내받았는데 다음 날에도 의자가 그대로였어요. 다시 연락하니 처음부터 상황을 설명해야 했어요.” | 완료된 접수 건에서 미해결 사유를 전달하고 재처리를 요청할 수 있어야 한다. | F | “다시 연락할 때 이전 접수 내용을 어떻게 확인했나요?” |
| I-04 / 질문 4 | “처음에는 어느 메뉴로 들어가야 할지 몰라서 친구에게 물어봤어요. 짧은 쉬는 시간에 하려다 결국 나중으로 미뤘어요.” | 처음 이용하는 학생도 별도 안내 없이 짧은 시간 안에 문제 접수를 완료할 수 있어야 한다. | NF·사용성 | “어느 단계에서 멈췄나요? 접수를 마치는 데 어느 정도 시간이면 괜찮을까요?” |
| I-05 / 질문 5 | “제출을 눌렀는데 화면이 한참 그대로여서 접수가 됐는지 모르겠더라고요. 기다리다가 버튼을 다시 눌렀어요.” | 제출 후 접수 성공 여부를 확인하는 응답 시간이 짧아야 한다. | NF·성능 | “얼마나 기다렸나요? 다시 누르기 전까지 몇 초 정도 기다릴 수 있나요?” |

## 4. 결산 요약 — 예시 발언에서 도출한 후보

### 4.1 새 기능 요구 2개

| ID | 새 요구 후보 | 근거 | 기존 기획과의 차이 |
|---|---|---|---|
| NEW-F-01 | 시스템은 담당자가 접수 건에 보완 요청을 등록하면 신고자가 해당 건에 추가 답변을 등록할 수 있도록 해야 한다. | I-02: 최초 접수와 추가 설명이 분리되어 전달 여부를 확인하기 어려움. | 기존 접수·처리 조회에 없는 **접수 이후 양방향 보완**이다. |
| NEW-F-02 | 시스템은 신고자가 완료된 본인 접수 건에 미해결 사유를 입력하면 해당 건의 담당 부서에 재처리 요청을 등록해야 한다. | I-03: 완료 안내 후에도 문제가 남아 처음부터 다시 설명함. | 기존 처리 상태 조회에 없는 **완료 후 재처리 요청**이다. |

### 4.2 측정 가능한 비기능 요구 2개

| ID | 분류 | 요구 문장 | 근거 |
|---|---|---|---|
| NEW-NF-01 | 사용성 | 처음 사용하는 학생 5명에게 학교 인증을 마친 첫 화면에서 동일한 문제 접수 과제를 주었을 때, 4명 이상이 도움말이나 진행자의 설명 없이 3분 이내에 접수를 완료해야 한다. | I-04: 처음 이용할 때 메뉴를 찾지 못해 접수를 미룸. |
| NEW-NF-02 | 성능 | 학교 정보 연동과 네트워크가 정상인 시험 환경에서, 유효한 문제 접수 10회를 각각 제출했을 때 모든 회차에서 제출 버튼을 누른 시점부터 접수번호가 표시될 때까지 3초를 넘지 않아야 한다. | I-05: 접수 여부를 알 수 없어 버튼을 반복해서 누름. |

수치(학생 5명 중 4명, 3분, 10회·3초)는 측정 가능한 문장으로 바꾸기 위한 **분석가의 제안값**이며, 고객이 실제로 제시하거나 합의한 값이 아니다. 실제 인터뷰에서 허용 시간과 이용 상황을 확인하여 조정한다.

현재 SRS의 5개 기능은 최초 접수와 진행 상황 확인에 집중한다. 위 예시에서는 접수 뒤 설명을 보완하거나 완료된 문제를 다시 다루는 과정이 추가 요구 후보로 나타났다. 실제 발언 확인과 팀 검토 후 백로그 반영 여부를 결정한다.
